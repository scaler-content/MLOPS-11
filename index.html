Overview

From hand-built infrastructure to a managed platform

Every model built so far in this track was trained on a local machine, packaged into a container, and shipped by hand — the Dockerfile, the FastAPI app, the load balancer, the health check, the scaling, all written from scratch. That approach works, and it teaches every moving part. But it also means owning every moving part.

SageMaker is AWS's managed machine learning service. Its pitch: hand over the parts that are identical for every model. Feed it data in S3 and point it at an algorithm or a container. It rents a machine to train on and discards that machine the moment training ends. It then puts the resulting model behind an HTTPS endpoint with logging, metrics, and autoscaling already wired in.

The work splits across two distinct roles on a real team, and this material walks through both.

ROLE 01

Platform engineer

Builds the network, the IAM role, and the SageMaker domain — the infrastructure every model will run inside.

ROLE 02

ML engineer

Connects an editor to a machine inside that network and does the actual data and model work in code.

Where this is headed

This post covers getting the platform and the data ready: the network, the identity layer, and a clean, correctly-shaped dataset sitting in S3. A second stage (not covered here) takes those four prepared files and trains & serves an actual model three different ways.

Architecture

Where SageMaker fits

SageMaker gives you the same pieces a hand-built deployment needs — a machine to run on, a network, an address, something watching it — already joined together. Everything in the system communicates through one place: S3. Nothing talks to anything else directly, which is also what makes the system debuggable: if you know where each piece reads and writes in S3, you can trace almost any problem.

The entire data flow, reduced to one hub and four spokes

SageMaker has dozens of features, but four of them carry most of the weight on a real team, and all four are normally driven from code rather than console forms — code can be reviewed, kept in version control, and re-run next month with one changed line. A form filled in by hand cannot.

Renting a large machine for twenty minutes beats owning one outright.

02

Tracks which model version is currently live.

Low-code tools like Canvas and Data Wrangler exist alongside this, aimed mostly at analysts rather than engineers — they resurface later in the context of where they actually fit.

The Project

Predicting returns for an online shop

The project throughout is an online shop selling clothes, shoes, electronics, home goods, beauty products and books. More than one order in five comes back, and every return costs shipping in both directions — the item often can't be resold at full price. If the shop knew at checkout which orders were likely to return, it could act early: show a size guide, confirm a cash-on-delivery order, or plan stock for items that tend to come back.

The question the model answers

When an order is placed, how likely is it to be returned? The label is yes/no — binary classification — and the model's output is a probability between 0 and 1.

The data is one CSV, returns.csv, with 12,000 past orders, one row per order. It's synthetic, generated from known rules so that whatever a tool finds can be verified — but it's shaped like a real export from a shop's order database, mess included: a header row, text categories, missing values, and the label in the last column.

Bills until you log out

Canvas bills from the moment it opens until you explicitly log out of it — closing the browser tab does not stop the meter. Left open, it costs roughly $1,400/month.

Bills while it exists

The NAT gateway and interface endpoints bill every hour they exist, used or not — about $120/month if forgotten. A real-time endpoint left running costs roughly $84/month.

Storage

S3, the place everything meets

S3 stores files — called objects — inside buckets. A bucket name is unique across all of AWS, not just one account, so names usually carry initials or a date to stay unique.

Inside a bucket there are no real folders. An object's name can contain slashes (train/train.csv), and the console displays the part before the slash as if it were a folder. That part is called a prefix, and SageMaker asks for prefixes constantly: told to read s3://bucket/train/, a training job reads every object whose name starts with train/.

PrefixHoldsWritten by
raw/The orders CSV as it arrivesManual upload
train/, validation/Training files in XGBoost formatData prep script
batch-input/, batch-labels/Rows to score, and their answers kept asideData prep script
output/The trained model, model.tar.gzThe training job
batch-output/Scores for those rowsThe batch transform job

Block Public Access stays on throughout — nothing in this setup needs a public bucket. SageMaker reads it entirely through the IAM role described below.

Infrastructure

A private network for SageMaker

Companies holding customer data put their ML machines in private subnets, where nothing on the internet can start a connection to them. A SageMaker domain configured this way is called VPC only. Private machines still need two ways out: to AWS services (S3, SageMaker itself), and to the open internet for things like pip install.

VPC endpoints

Private doors from the VPC to one AWS service each. Traffic through them never leaves AWS's own network.

NAT gateway

Lets machines in private subnets start connections outward, while nothing outside can start one in — a one-way door.

Two private subnets, one outbound door, and private doors to AWS services

Interface endpoints aren't free — six of them cost about $0.12/hr combined, every hour they exist, which is why they get deleted at the end of a session rather than left running between sessions.

On stricter networks

Some teams remove the NAT gateway entirely, so every outbound call must go through an endpoint. It works, but the gaps are hard to find — a domain missing even one needed endpoint (Athena, Glue, EMR Serverless, or Cognito, for Canvas specifically) can leave a tool's UI spinning indefinitely with no error at all. A common middle ground keeps the NAT gateway but puts an allow-list proxy or firewall in front of it.

Identity & Access

A role, a domain, and a space

A domain is SageMaker's container for users, their settings, their network, and the role their work runs as. Inside it, each person gets a user profile. A space is a named disk plus a machine that runs an editor on top of it — the machine can be stopped while the disk persists.

1

IAM role

Every script and every job acts as one role. A managed policy covers SageMaker itself; a small custom policy names the bucket explicitly, since the managed policy only covers buckets with "sagemaker" in the name.

2

Domain

Created as VPC only, pointed at the private VPC, its subnets, and the role from step one.

3

User profile & space

A named disk plus a machine, created inside the domain, with remote access turned on so an external editor can connect.

4

Remote connection

An editor on a laptop opens a tunnel into the space through Systems Manager — no port is ever opened to the internet.

What the role is actually allowed to do

A managed policy covers creating and running SageMaker resources — training jobs, endpoints, domains, spaces. It's broad by default: it can create any SageMaker resource in the account, which a stricter team would narrow down to a hand-written action list.

A custom inline policy names the bucket explicitly, in two parts: permission to list the bucket itself, and separately, permission to read/write/delete the objects inside it. Both are required — a policy covering only the bucket listing lets a role see a file's name without being able to download it.

Connecting an editor to a space calls a specific session-start action that the broad SageMaker policy does not include. A dedicated policy grants it, scoped so a user can only start a session on spaces belonging to their own profile. Missing this permission produces a vague, unhelpful connection failure with no indication the role is the cause.

Idle shutdown

A JupyterLab space bills while it runs, connected or not. Idle shutdown stops it automatically after a set period of inactivity — the minimum allowed is 60 minutes, which exists specifically because people forget to stop spaces manually.

Exploration

A first look at the data

With the role in place, code running on the space reads straight from S3 — the downloaded bytes go directly into a dataframe, nothing touches disk. A first pass over returns.csv surfaces the shape of the problem immediately.

MetricValue
Rows × columns12,000 × 14
Return rate22.8%
Missing values502, all in seller_rating

A model that always predicted "not returned" would be right 77% of the time — which is exactly why this kind of problem gets judged by AUC rather than raw accuracy. Accuracy rewards the lazy answer; AUC measures how well the model ranks returned orders above non-returned ones across every possible threshold.

The Trap

A column from the future

Most columns in the dataset describe an order as it looked the moment it was placed. One does not. refund_amount is only filled in after a return has already been processed — for an order that was never returned, it's always zero. That's a textbook case of target leakage: a column holding information that would not exist yet at the moment a real prediction is needed.

A model will happily learn from a leaking column anyway, and its scores will look spectacular right up until it meets production data, where that column is always zero by definition.

1.000

A perfect AUC. On real data, a perfect score almost always means a leak — the model didn't learn anything about why orders return, it learned that a non-zero refund means a return.

The honest number, with the leaking column removed, is 0.706 — a modest score, and modest is normal here. Whether a customer sends something back depends heavily on things the shop simply never observes. From this point on, refund_amount is dropped entirely.

Checkpoint — think it through

Pick another column and ask whether it's actually known at the moment the order is placed. Try delivery_days: is the number of days a parcel took to arrive known when the order goes in, or only estimated? Reasoning about when each column becomes known catches leaks no automated tool can find on its own, because the tool doesn't know the business.

No-Code Tooling

Finding the same leak without writing code

Data Wrangler, reached through SageMaker's no-code workspace Canvas, profiles a dataset and generates an automatic report. Pointed at the same CSV, it independently flags refund_amount as high target leakage — and even suggests the fix, a drop-column transform.

Its feature-power table scores each column's predictive strength in isolation. The gap between the top two explains exactly why the warning fired:

refund_amount
0.583
price
0.271

refund_amount scores more than double the next strongest column on its own — a strong signal that it isn't really a feature, it's an answer key.

Where this kind of tool actually fits

The warning is genuinely useful, and an analyst with no Python gets it in a few clicks. But the work inside such a flow lives inside the tool itself. On an engineering team, the cleaning logic belongs in code that goes through version control, review and CI. A fair way to use a profiling tool like this: look at a new dataset fast, find the obvious problems, then write the actual fix where the rest of the code already lives.

Data Preparation

Getting the data into the shape XGBoost expects

SageMaker's built-in algorithms are ready-made, AWS-maintained training containers — no training code to write. The trade-off: the data must arrive in exactly the format the algorithm expects. For the built-in XGBoost container reading CSV, that means three strict rules.

RULE

Label first

The target column goes in the first position, not the last.

RULE

No header row

A header, left in by mistake, gets silently read as one row of data.

RULE

Numbers only

Categories such as "apparel" must already be one-hot encoded into 0/1 columns.

The three-way split

70% · train
15%
15%
Train · 8,400 rows Validation · 1,800 rows Batch (held out) · 1,800 rows

The batch split deliberately has its label column stripped out before it's used for scoring — a model being asked for predictions shouldn't be handed the answers. Those answers are kept aside separately, to check the batch scores afterward.

What happens if the header row is left in by accident

The built-in algorithm doesn't validate the input format — it reads whatever it's given. With a header row left in a training run, the job didn't fail. Its log simply reported one extra row of training data than actually existed, because the header's text got silently coerced into missing values. The model came out nearly identical, since one bad row out of thousands barely moves anything — but a larger mistake of the same kind would fail just as silently. The row count in the job log is the only tell, so it's worth reading.

Feature order matters

After encoding, 18 feature columns remain in a fixed order. Whatever consumes this data later — a training job, an endpoint — expects exactly these columns, in exactly this order, and nothing checks it automatically:

Summary

What this stage actually accomplished

The work split across two roles. As platform engineer: a private network with no inbound path from the internet, VPC endpoints for the AWS services carrying data and control traffic, a NAT gateway as the one-way door out, a scoped IAM role, and a VPC-only domain joining it all together. As ML engineer: a remote editor connected into that network, doing the actual data work in plain Python files — which is where this kind of work tends to live on a real team.

The data itself had one real trap. A leaking column scored a perfect AUC until it was removed, and two small models run side by side exposed it in seconds — a no-code profiling tool found the same thing without any code at all. From there, the raw export was reshaped into the strict format the built-in XGBoost algorithm requires: label first, no header, numbers only.

The recurring theme

Nearly every failure along the way was quiet rather than loud: a missing permission with an unhelpful error, a missing network endpoint that just spins forever, a header row read silently as data. None of it raised a clear exception. Catching it came down to actually reading the numbers and the logs, not trusting that something would shout if it was wrong.
